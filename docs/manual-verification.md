# MeshMind 手工验证清单

## CI 已覆盖哪些、这份清单还剩哪些

自 2026-08-16 起，仓库 `LingyiChen-AI/MeshMind` 上有 GitHub Actions CI
（`.github/workflows/ci.yml`，**macOS + Windows 双平台矩阵**），每次 push 到 `main` 都会跑。

**以下项目已由 CI 在两个平台上自动覆盖，人工不必重复：**

- 前端单元测试（`pnpm test`）与类型检查 / 构建（`pnpm build`）
- Rust 全量测试（`cargo test --workspace --locked`）
- Clippy（`-D warnings`）与 `cargo fmt --check`
- **界面交互测试**（`pnpm e2e`，Playwright + 假 IPC，两个平台各跑一遍）：
  自动保存的数据安全（附件 id 有没有一起传回去、保存失败后内容会不会丢、
  慢保存时会不会并发写同一条）、跨窗口事件、退出前的落盘时序、
  搜索 / 回收站 / 设置 / 标签筛选 / 分页的调用形状，以及 **AI 问答的调用形状**
  （启用前只发只读的预览、确认框点取消一个调用都不发、流式事件的归并与迟到事件的丢弃、
  引用跳转带的是哪个 noteId、语义分组的显隐）。
  **注意它测的是「前端向后端发了什么调用」，不是「后端做对了没有」**——
  后端被一份内存假实现顶掉了，所以真实的 SQLite 行为、全文索引、
  热键注册、Dock 图标切换一概不在覆盖范围内，仍然要靠下面的人工清单。
- **CSP 违规守卫**（`e2e/csp.spec.ts`）：把 `tauri.conf.json` 里的**生产** CSP 真的挂到
  文档响应头上，再走一遍主窗口 / 附件图片 / 搜索 / 设置 / 回收站 / 快捕窗口，
  断言全程零违规。详见下面「内容安全策略（CSP）」一节——**它验到了什么、验不到什么，
  那一节写得很细，收紧策略之前先读它。**
- **安装包能否产出**：macOS 出 `.dmg`、Windows 出 `.msi`，产物上传到 run 的 artifacts（保留 7 天）

也就是说「代码在 Windows 上能不能编、测试过不过、包打不打得出来」这类问题，
现在由 CI 兜底，不用再人肉在 Windows 机器上跑一遍。
下载 CI 产出的安装包（`gh run download <run-id>`）直接拿来做人工验证即可。

**以下仍然只能人工做，CI 结构上够不着：**

- 窗口行为（显示 / 隐藏 / 多显示器 / DPI 缩放）
- 全局热键（注册、双触发过滤、与输入法冲突、被占用时的降级）
- 系统托盘（图标观感、菜单项、退出后进程是否真的消失）
- 真实剪贴板（截图粘贴、富文本粘贴）
- **真机安装**（Gatekeeper 放行、WebView2 缺失时的引导、中文用户名账户）
- 数据目录的真实落盘与迁移、强杀进程后的 SQLite WAL 行为

下面的清单就是这剩下的部分。

## 这份清单是干什么的

自动化测试（`pnpm test` / `cargo test --workspace`）只能覆盖纯逻辑：数据库、检索、命令层的输入输出。
**窗口行为、全局热键、系统托盘、真实剪贴板、真机安装包**这些依赖操作系统和用户交互的部分，
CI 里跑不了，也没法可靠地断言，只能人工确认。这份清单就是这部分的覆盖面。

### 使用要求

- **macOS 与 Windows 各完整跑一遍**，两个平台等同对待，不允许「在 mac 上过了就默认 Windows 也行」。
- 用**安装包装出来的正式应用**验证（`.dmg` / `.msi`），不要用 `pnpm tauri dev`——
  dev 模式下托盘、单实例、打包路径、数据目录的行为和正式包不一致。
- 标注了 `[macOS]` / `[Windows]` 的条目只在对应平台执行，其余条目两个平台都要执行。
- 建议**从干净状态开始**：验证前先删掉应用数据目录（见「平台专属」一节的路径），
  这样「重启后数据还在」「首次权限授予」这类条目才有意义。
- 发现问题就地记录：条目前打 `[x]` 表示通过，不通过的在条目下补一行现象 + 复现步骤。

## 通用功能：笔记与编辑

- [ ] 新建笔记，输入文字，停手约 1 秒后，左侧列表出现该条
      （右上角有「已保存 / 未保存 / 保存中」状态指示，可以对照状态流转是否正确）
- [ ] 正文里写 `#标签`，保存后列表上显示该标签
- [ ] **点侧边栏顶上的标签 chip 做筛选**，列表只剩带该标签的笔记；再点一次回到全部
      （这条曾经因为外壳漏注册 `list_notes_by_tag` / `list_all_tags` 而整个是死的，
      而清单上一直没有它，所以三轮人工验证都没碰到——见下面的注）
- [ ] 删除笔记后，列表里不再出现，搜索也搜不到
- [ ] **回收站里点「彻底删除」和「清空回收站」都真的执行**，不是点了没反应
      （同上，`purge_note` / `purge_all_deleted` 也曾漏注册）
- [ ] 重启应用后，笔记、标签、图片都还在

> 注：上面两条带「曾经」的条目对应一次真实缺陷——`ui/lib/ipc.ts` 调的命令
> 在 `crates/shell/src/main.rs` 的 `generate_handler!` 里没注册，TS 和 Rust 两边
> 都不会报错，只在运行时 reject「Command xxx not found」。现在
> `e2e/contract.spec.ts` 会把三份命令清单对起来，同类问题不会再溜过去；
> 但**人工清单上的这两条仍然要留着**——契约守卫只保证命令注册了，
> 不保证它接上去之后行为是对的。

## 通用功能：搜索

搜索入口：`⌘K`（macOS）/ `Ctrl+K`（Windows）。
以下条目建议先建一篇标题或正文含「知识图谱」的笔记再验。

- [ ] 中文前缀：输入「知识图」能命中「知识图谱」
- [ ] 全拼连写：输入 `zhishitupu` 能命中
- [ ] 拼音首字母：输入 `zstp` 能命中
- [ ] 两字母首字母：输入 `zs` 能命中
      （这条走的是 LIKE 兜底路径，和 trigram 是**不同的代码路径**，必须单独验，不能因为 `zstp` 过了就跳过）
- [ ] 搜索结果上的来源标签正确：字面命中标「字面」、全拼命中标「全拼」、首字母命中标「首字母」
- [ ] 字面命中时，命中词在结果里被高亮
- [ ] **拼音命中不高亮是有意设计**，不要当 bug 报
      （拼音串在原文里根本不存在，无法定位到具体字符区间）；
      这条要确认的是「不高亮但结果正确」，而不是「高亮错位置」
- [ ] 跨段落假阳性：建一篇多段落笔记，第一段以「…知识」结尾、第二段以「图谱…」开头，
      搜「知识图谱」**不应**命中这篇

## AI 与知识问答

入口：右侧问答栏 `⌘L`（macOS）/ `Ctrl+L`（Windows）；配置在「设置 → AI 与知识问答」。

**这一整节都必须用真实的模型服务验。** e2e 里那份假实现只能证明「前端向后端发了什么调用」，
证明不了「模型真的答了什么」，更证明不了「有没有东西离开这台机器」。
准备两样东西：一个 OpenAI 兼容的服务（DeepSeek 或任意自建网关）和一个本机 Ollama，
两条都要走一遍。**建议全程开着抓包工具**——这一块唯一真正要紧的问题是
「什么时候有网络请求、请求里带了什么」，而那在界面上完全看不见。

### 默认关闭（spec §13.1）

- [ ] 全新安装、**不做任何 AI 配置**：行为和加这个功能之前完全一致
- [ ] **一个出站请求都没有**（抓包确认，或直接断网用一整轮：不该有任何报错或卡顿）
- [ ] 右侧问答栏是引导态：「先在设置里配置 AI 服务」并说出缺的是哪一项，**没有输入框**
- [ ] 搜索面板里没有「语义相关」这一组，**也没有「检索中…」**
      （分不清「没开」和「没匹配」时宁可什么都不显示，搜索框不该变成 AI 的广告位）
- [ ] 活动监视器 / 任务管理器里看不到向量化线程的持续占用

### 配置与启用（§13.2）

- [ ] 填好 Base URL / 密钥 / 对话模型 / Embedding 模型后点「测试连接」：
      embedding 与对话**分两行报**（embedding 通了而对话不通——模型名写错——是很常见的半通状态，
      合成一句「连接成功/失败」就查不出来了）
- [ ] 打开总开关：先弹出「将为 N 篇笔记建立索引，会调用你配置的模型服务并产生费用，继续？」，
      **抓包里这时一个模型请求都没有**
- [ ] 点「取消」：提示「已取消，AI 保持关闭」，开关回到关闭位，**抓包里仍然一个请求都没有**
- [ ] 再打开、点「继续」：索引开始跑，「待索引 N 篇 · 已索引 N 块 · 内存 x MB」这三个数字会动
- [ ] 关掉设置面板，索引在后台继续；重新打开面板数字接着往下走
- [ ] 索引跑完后不出现「上一次索引失败」；真出现了，「重试全部」能把失败的重新入队

### 提问（§13.3、§13.4）

- [ ] 问一个**只有自己笔记里才有答案**的问题：**先看到引用条，再看到文字一段段流出来**
      （引用先到是刻意的：用户要在模型开口之前就看见它读了哪些笔记）
- [ ] 回答里说的东西，能在被引用的那几篇笔记里逐条找到
- [ ] 点引用条、点正文里的 `[n]`，都跳到**正确的那篇**笔记，而且**问答栏保持打开**
- [ ] 问一个笔记里根本没有的问题：回答是「笔记里没有找到相关内容」这类说法，
      **不是编造一段听起来很像的内容**。这条最重要也最容易蒙混过关，要逐字读回答
- [ ] 长回答滚动时往上翻去看引用：**不会被后到的文字一路拽回底部**
- [ ] 搜索面板（`⌘K` / `Ctrl+K`）里出现「语义相关」分组，
      且**和「关键词匹配」组重合的那几篇不会重复出现**

### 中断与失败（§13.5）

- [ ] 回答到一半点「停止」：文字停下，提示「已停止生成，这次的回答没有保存」，
      **没有红色错误横幅**（取消不是错误）
- [ ] **拔网线**（或关掉本机 Ollama）再提问：错误横幅可读、说得出原因，
      消息流里**不留半截助手消息**，但**自己敲的那句问题还在**；
      插回网线再问一次能正常回答
- [ ] 故意把密钥改错再提问，**逐字读那句报错**：里面不许出现密钥的任何一段，
      也不许出现 `Authorization` 头
- [ ] 回答途中切到别的会话、或点「新对话」：正在跑的那次停掉，
      **新的那次不会莫名其妙地显示「已停止生成」**（那是上一次的取消事件迟到了）

### 换模型与重建（§13.6）

- [ ] 改 Embedding 模型名并让输入框失焦：出现「建议现在重建索引」的提示，且说得出旧模型名
- [ ] 点「重建索引」→ 二次确认 → 全部重新入队；跑完后检索结果仍然正确
- [ ] 换了模型但**不重建**就直接检索：设置面板出现
      「有 N 条向量来自其他模型（维度对不上，已被跳过）」
      （不提示的话，库里同时躺着两个模型的向量，拿不同空间里的数比大小，
      结果毫无意义且没有任何报错）

### 关闭 AI（§13.7）

- [ ] 关掉总开关：**不弹确认框，立刻生效**
- [ ] 右侧问答栏回到引导态，这次那句话是「AI 还没启用」而不是「先在设置里配置」
- [ ] 搜索面板里的「语义相关」分组消失，**「检索中…」也不再出现**
- [ ] 活动监视器 / 任务管理器里向量化线程的持续占用消失
- [ ] 关掉之后再用一整轮（写笔记、搜索、快捕）：**抓包里一个出站请求都没有**

### 两类服务都要走一遍

- [ ] OpenAI 兼容：Base URL 带 `/v1`（如 `https://api.deepseek.com/v1`），索引 + 提问 + 语义搜索都通
- [ ] Ollama：Base URL 是裸的本机端口（如 `http://localhost:11434`），同上
- [ ] **从 OpenAI 切到 Ollama 之后**：库里那份旧密钥**不会**自己消失。
      界面上应当**仍然显示「API Key：已设置」并给得出「清除密钥」按钮**——
      整块藏掉的话，用户既不知道这台机器上还存着一份可计费的凭证，也没有地方把它清掉
- [ ] 点「清除密钥」之后，Ollama 模式下那一整块才消失

### 密钥与数据库文件（§9.2）

- [ ] 设置面板上「密钥保存在本地数据库中，请勿分享该文件」这句话可见
- [ ] **备份、同步（iCloud / OneDrive / Dropbox）、或把 `meshmind.db` 发给别人之前，
      必须知道这个文件里存着明文 API Key——拿到这个文件的人等于拿到了可计费的凭证。**
      验证方式：用任意 SQLite 工具打开数据库，跑
      `SELECT value FROM settings WHERE key = 'ai.api_key';`，确认自己看见的就是那串明文
      （macOS：`~/Library/Application Support/com.meshmind.desktop/meshmind.db`；
      Windows：`%APPDATA%\com.meshmind.desktop\meshmind.db`）
- [ ] 密钥**不经 IPC 回到前端**：开 DevTools 看 `get_settings` 的返回，
      里面只有 `ai.api_key_set`（`"true"` / `"false"`），**没有** `ai.api_key`。
      这条保证了密钥不会出现在前端日志、错误上报或用户截图里

（§13.8「两个平台 CI 全绿、打包产物能起来」由 CI 覆盖，见本文开头那一节。）

## 快捕窗口与全局热键

热键：macOS `Opt+Space`，Windows `Ctrl+Alt+Space`。

- [ ] 按热键唤起快捕窗口，**再按一次收起**
- [ ] **重点**：如果出现「按了跟没按一样」（弹出后立刻消失，看起来毫无反应），
      说明 Pressed / Released 双触发的过滤失效了——这是最容易回归的地方
- [ ] 长按热键不放，窗口不会疯狂闪烁（重复按键事件被正确忽略）
- [ ] 快捕窗口**二次唤起**后，光标直接在编辑区，不需要先点一下才能打字
      （窗口是 hide/show 复用、组件不卸载，`autoFocus` 只在首次挂载生效，这里打了 focus 补丁，专门验第二次以后）
- [ ] 主窗口和快捕窗口**同时开着**，在快捕里按 `⌘Enter` / `Ctrl+Enter` 保存，
      主窗口列表**立刻**多出一行（跨窗口事件广播，不需要手动刷新）
- [ ] 快捕里只粘一张图、一个字不打，也能保存成功（纯图片笔记不算空内容）
- [ ] 快捕里有内容时按 `Esc`，弹出二次确认，而不是直接丢弃
- [ ] `[macOS]` 中文输入法下按 `Opt+Space`：正常情况这个组合会输入不换行空格（U+202F），
      确认热键把它**截获**了，没有漏一个空格进输入框
- [ ] `[Windows]` 确认 `Alt+Space` 仍能正常弹出系统窗口菜单（我们注册的是 `Ctrl+Alt+Space`，不应误伤）
- [ ] `[Windows]` 确认热键不与输入法（微软拼音 / 搜狗等）的快捷键冲突
- [ ] 热键被占用的降级路径：先用别的软件占掉该热键，再启动 MeshMind →
      托盘 tooltip 显示 ⚠ 警告文案，且托盘菜单里的「快速捕捉」仍然可用
- [ ] `[macOS]` **已知覆盖盲区**：首次运行、未在「系统设置 → 隐私与安全性 → 辅助功能」授权时，
      热键可能**静默失效**（注册看起来成功，但收不到事件）。
      请实测确认表现，并记录：是完全没反应、有没有提示、授权后是否需要重启应用才生效

## 平台专属

- [ ] `[macOS]` 数据落在 `~/Library/Application Support/com.meshmind.desktop/`
- [ ] `[Windows]` 数据落在 `%APPDATA%\com.meshmind.desktop\`
- [ ] `[macOS]` `.dmg` 安装后能正常启动。
      **应用没有做 Apple 代码签名与公证**，从浏览器下载会被打上 `com.apple.quarantine`
      隔离属性，首次打开系统会报 **「已损坏，无法打开，你应该将它移到废纸篓」**。
      包并没有坏（`codesign -dv` 能看到 `Signature=adhoc`，是 Rust 构建 arm64 时
      链接器自动加的），是 Gatekeeper 对「adhoc 签名 + 隔离属性」的处理结果。
      **注意：近几版 macOS 上「右键点打开」对这种情况已经不再管用**，别照老经验指导用户。
      可行的两条路：
        - `xattr -cr /Applications/MeshMind.app`
        - 系统设置 → 隐私与安全性 → 找到被阻止的 MeshMind → 「仍要打开」
      这是「不做签名」的固有代价，不是缺陷。要彻底消除只能买 Apple 开发者账号做签名+公证。
- [ ] `[macOS]` 通过**应用内自动更新**装上的版本，重启后能直接打开、不再报「已损坏」。
      更新包由应用自己下载写入，不经过浏览器，理论上不会被打隔离属性——
      但这一条必须实测，它决定了用户装过一次之后是否就永远顺畅了
- [ ] `[Windows]` `.msi` 安装后能正常启动
- [ ] `[Windows]` 在**没有装 WebView2 Runtime** 的机器（干净的 Windows 10 虚拟机）上安装，
      有安装引导 / 自动拉起 WebView2 安装，而不是启动后白屏或直接崩

## 内容安全策略（CSP）

`crates/shell/tauri.conf.json` 的 `app.security` 现在是一份真策略（此前是 `csp: null`，
即完全关闭）：

```
csp    : default-src 'self'; img-src 'self' blob: data:; style-src 'self' 'unsafe-inline';
         script-src 'self'; connect-src 'self' ipc: http://ipc.localhost; font-src 'self' data:;
         object-src 'none'; base-uri 'self'; frame-ancestors 'none'
devCsp : 同上，但 script-src 额外给 'unsafe-inline' 'unsafe-eval'，connect-src 额外给
         ws://localhost:1420 http://localhost:1420（vite 的 HMR 要内联脚本、eval 和 websocket，
         拿生产策略跑 `pnpm tauri dev` 会直接白屏）
```

非默认指令的理由：

- **`img-src` 的 `blob:` 是命门**。附件图片全部走 `URL.createObjectURL` 产生的 blob URL 渲染
  （见 `ui/lib/attachments.ts` 顶部关于「为什么不用 asset 协议」的说明），漏了它每一张图都碎，
  而且**页面不报错、不白屏，只是图没了**。
- **`style-src` 的 `'unsafe-inline'`**：TipTap / ProseMirror 会往节点上写内联样式，
  vite dev 也靠 JS 注入 `<style>`。暂时留着。
- **`connect-src` 的 `ipc:` / `http://ipc.localhost`**：Tauri 2 的 IPC 通道，
  分别对应 macOS 与 Windows 两种形式。
- `object-src 'none'` / `base-uri 'self'` / `frame-ancestors 'none'` 是纯收紧，没有代价。

### 自动化已覆盖（人工不必重复）

`e2e/csp.spec.ts` 用 `page.route()` 拦下文档响应、**把配置里的生产 `csp` 原样加成
`Content-Security-Policy` 响应头**（从配置文件读，不在测试里抄第二份），同时从
Chromium 控制台和页面的 `securitypolicyviolation` 事件两路收集违规，逐步断言零违规：

- 应用启动、主窗口渲染、笔记列表出现
- **打开一条带附件图片的笔记，图片真的显示出来**（断言 `img` 的 `naturalWidth > 0`，
  被 CSP 拦下时它停在 0）——这是 `img-src blob:` 的直接验证
- ⌘K 打开搜索面板并输入、打开设置面板、打开回收站
- 快捕窗口渲染并输入

外加两条守「守卫本身」的测试：策略被改回 `null` 时立刻红；运行时插一段内联脚本，
必须真的被 `script-src` 拦下（证明响应头确实生效，而不是一路空跑出来的假绿）。

### 这份守卫**验不到**什么 —— 人工只需确认这些

不要因为 CI 绿了就跳过本节。守卫跑在 Playwright + vite dev server + Chromium 上，
以下四类问题它结构上够不着：

1. **Tauri 注入到真实 webview 的初始化脚本**。真机上 Tauri 会往页面里注入 IPC 桥与各插件的
   引导脚本；vite dev server 上一行都没有（e2e 的假 IPC 走 CDP 注入，不受 CSP 管辖）。
   这些注入脚本会不会被 `script-src 'self'` 挡下来，只有真机能回答。
2. **`connect-src` 里的 `ipc:` 与 `http://ipc.localhost`**。假 IPC 是内存函数，不发真实请求，
   这两项在自动化里既没被用到也没被验证。
3. **生产策略与 dev 策略的差异**。守卫用的是生产 `csp`，而 `pnpm tauri dev` 跑的是更宽松的
   `devCsp`；反过来 `devCsp` 自己写错（比如漏了 ws 端口导致 HMR 断掉）守卫也测不出来。
4. **WKWebView / WebView2 与 Chromium 的解释差异**。三个引擎对 `blob:`、自定义协议、
   `'self'` 是否覆盖 `ws:` 的处理并不完全一致，Chromium 上的结论只在 Chromium 上成立。

另需知道：vite dev 会往首页注入一段**内联** module 脚本（react-refresh preamble），
生产策略必然拦它。守卫的做法是只在**响应头**里补一个 `'nonce-…'`，并只贴给文档里
没有 `src` 的 `<script>`——`tauri.conf.json` 里的策略一个字都没改，发出去的仍是严策略。
另有一条测试钉住「仓库 `index.html` 里没有内联脚本」，防止应用自己加了内联脚本被这个
nonce 顺手放行。

于是人工只剩下面这几条（**每条之后都看一眼 devtools 控制台有没有
`Refused to ... because it violates the following Content Security Policy directive`**）：

- [ ] `pnpm tauri dev` 起来后应用**不白屏**（验的是 `devCsp` 本身可用，以及 HMR 的 ws 没被挡）
- [ ] 用**安装包装出来的正式应用**（`.dmg` / `.msi`，走的才是生产 `csp`）启动后不白屏，
      主窗口正常渲染 —— Tauri 注入脚本被挡的话，症状就是白屏
- [ ] 正式应用里**粘贴一张截图，图片显示出来**；重开应用后打开这条笔记，图片仍然显示
      （真机上的 blob URL 路径 + 真实 webview 对 `blob:` 的处理）
- [ ] 正式应用里 IPC 真的通：新建笔记能保存、搜索有结果、设置面板能改热键
      （任何一条不通都可能是 `connect-src` 少了 `ipc:` / `http://ipc.localhost`）
- [ ] 在编辑器里**拖动图片节点**（ProseMirror 会写内联样式，验 `style-src 'unsafe-inline'`）
- [ ] 唤起快捕窗口，粘图并保存
- [ ] **macOS 与 Windows 各做一遍**：两个 webview 引擎对 CSP 的解释不同，
      一个平台过了不代表另一个平台过

发现 violation 时：**按提示加最小的那一项**，一次只改一条，不要图省事放 `*`；
改完把理由补进上面「非默认指令的理由」，并回 `e2e/csp.spec.ts` 看这条能不能顺手被自动化接住。

      Windows：`%APPDATA%\com.meshmind.desktop\attachments\`）

## 韧性与边界

这些是自动化测试结构上够不着的地方——真机、真文件系统、真窗口管理器才有意义。

- [ ] 快捕保存后窗口自己收起，且**内容已清空**。再次唤起时不应残留上次的文字
      （窗口是 hide/show 复用，组件不卸载，残留是这类复用的典型副作用）
- [ ] `[双屏]` 快捕窗口在多显示器下弹到当前活动屏幕，而不是跑到另一块屏
- [ ] `[Windows]` 在 125% / 150% 缩放下，快捕窗口尺寸与字号正常，不错位不模糊
- [ ] 搜一个必然搜不到的词，显示明确的「没有命中」空态，而不是一片空白
- [ ] 搜索框输入纯空格、emoji、以及 `%` `_` `'` `"` `*` 这类特殊字符，
      不报错也不返回诡异结果（`%` 和 `_` 是 SQL LIKE 的通配符，
      而 1-2 字符的拼音查询走的正是 LIKE 兜底这条独立代码路径）
- [ ] **正在自动保存时强杀进程**（活动监视器强制退出 / 任务管理器结束任务），
      重启后数据库不损坏、笔记不出现半截内容（验 SQLite WAL 的真实行为）
- [ ] `[Windows]` 用**中文用户名**的账户跑一遍——`%APPDATA%` 路径含非 ASCII 字符
      是 Windows 上很常见的翻车点，而 CI runner 的用户名永远是 ASCII
- [ ] 装了旧版本再装新版本，数据保留、迁移正常
      （MVP 阶段只有 v1 一个 schema 版本，这条现在跑不出问题，
      留作占位，避免第一次真正发版时才想起来）

## Windows 首次验证纪要（2026-08-16）

这是 Windows 侧**第一次**真正跑起来——在此之前所有 Rust / 前端代码只在 macOS 上验证过，
Windows 上一行都没执行过。记在这里是给三个月后的自己看的：同类问题会在加新依赖时重现。

**结果：首次 CI 双平台一次通过，无需修复。**

| 平台 | 结论 | 耗时 |
| --- | --- | --- |
| macos-latest | success | 约 7 分钟 |
| windows-latest | success | 约 13 分钟 |

Windows 上首次全部通过的步骤：`pnpm install --frozen-lockfile` → `pnpm test` →
`pnpm build` → `cargo test --workspace` → `cargo clippy -- -D warnings` →
`cargo fmt --check` → `pnpm tauri build --bundles msi` → 产物上传（约 7 MB 的 `.msi`）。

### 事前预判过、但实际没有发生的问题

推之前列了一张分诊表，逐条记下来为什么没炸——将来真炸了可以直接对照：

- **MSVC / `cl.exe` 找不到，`libsqlite3-sys` 编不过**：没发生。`windows-latest` 镜像自带
  Visual Studio Build Tools，默认 target 是 `x86_64-pc-windows-msvc`，`cc` crate 直接找得到。
  **不需要** `ilammy/msvc-dev-cmd`，也不需要装 LLVM / MinGW。
- **`pnpm install --frozen-lockfile` 报 lockfile 漂移**：没发生，`pnpm-lock.yaml` 与
  `package.json` 一致。
- **只在 Windows 上失败的测试（行尾 / 路径分隔符）**：没发生。推之前先加了 `.gitattributes`
  （`* text=auto eol=lf`）把行尾锁死，避开了 `include_str!` 的 SQL 与测试里多行字面量
  在 Windows 检出时被转成 CRLF 的风险。这是**预防性措施**，不是事后修复。
- **`tauri build` 找不到 WiX**：没发生，Tauri 首次运行会自己下载 WiX。
- **路径过长（260 字符限制）**：没发生。
- **`cargo fmt --check` 只在 Windows 上失败**：没发生，同样归功于 `.gitattributes`。
- **打包超时**：没发生。Windows 冷缓存全量编译 + 打包总共约 13 分钟，离超时很远。

### 结论与注意事项

- 现在 `main` 上每次 push 都会在两个平台产出安装包。**要人工验证时不必自己打包**，
  直接 `gh run download <run-id>` 拿 CI 的产物，这样验的就是 CI 真正产出的那个包。
- CI 的 cargo 命令带了 `--locked`：`Cargo.lock` 与 manifest 不一致会立刻失败，
  而不是 CI 悄悄改 lockfile 后照样通过（本项目踩过一次 lockfile 未提交）。
  **加新 crate 后记得把 `Cargo.lock` 一起提交。**
- CI runner 的用户名永远是 ASCII，**中文用户名下的 `%APPDATA%` 路径问题 CI 永远测不出来**，
  这条必须人工验（见「韧性与边界」一节）。
- 同理，WebView2 Runtime 在 runner 上是预装的，**干净 Windows 机器上的 WebView2 缺失引导
  CI 也覆盖不到**。
